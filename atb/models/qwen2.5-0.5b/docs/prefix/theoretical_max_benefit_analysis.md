# Shared Prefix 理论最高收益评估

> 测试日期: 2026-08-08 (分析基于 2026-08-05/06 的 profiling 数据)
> 测试环境: Ascend910_9382, 24 AI cores, 48 vector cores, AIC/AIV 1800MHz
> 模型: Qwen2.5-0.5B (24层, hidden=896, 14 q-heads, 2 kv-heads, head_dim=64, vocab=151936, fp16)
> 数据来源:
> - 无 prefix: `profiling_analysis_seq150_vs_seq218.md` (device 8, 干净对比)
> - 有 prefix: `profiling_analysis_prefix_caching.md` (device 4)
> - 算子级对比: `prefix_vs_noprefix_analysis.md`
> - GatherV2 单算子: `bench_gather_vs_split.md`
> - 原始 CSV: `profiling_data/` 下 4 个 PROF 目录

## 1. 方法论

### 1.1 核心思路

Prefix caching 通过去重 batch 内共享的 prefix tokens, 减少部分算子的计算量。要评估理论最高收益, 需要:

1. **建立线性模型**: 利用 seq150 vs seq218 (同一 device 8, 消除芯片差异) 的 per-token 耗时差异, 将每个算子分解为 `固定开销 + 可变开销 × token数`
2. **区分受益/非受益算子**: prefix caching 只压缩 FFN 侧算子 (expand→attention→compress→FFN), attention 侧 (Q/K/V proj + FIA + Rotary) 处理全 batch, 不受益
3. **推算不同去重率下的节省**: `节省 = 全batch_token数 × 去重率 × 受益算子可变开销`
4. **扣除开销**: GatherV2 expand/compress 开销 + attention 退化

### 1.2 去重率定义

```
去重率 r = 去重token数 / 总token数
         = prefix_len × (batch - 1) / (seq_len × batch)

唯一token数 = prefix_len + (seq_len - prefix_len) × batch
总token数   = seq_len × batch
```

**最大去重率**: 当 prefix_len = seq_len (所有请求完全相同) 时, r = (batch-1)/batch
- batch=10: r_max = 90%
- batch=20: r_max = 95%
- batch=100: r_max = 99%

## 2. 线性模型

### 2.1 模型构建

利用 seq150 (1500 tokens) 与 seq218 (2180 tokens) 的差值, 计算每个算子的固定/可变开销:

```
可变开销 V = (T_2180 - T_1500) / (2180 - 1500) = (T_2180 - T_1500) / 680
固定开销 F = T_1500 - V × 1500
```

### 2.2 受益算子 (prefix 模式下处理唯一 tokens)

| 算子 | 固定开销 F (us/iter) | 可变开销 V (us/token) | 全batch时间 (1500tok) | 说明 |
|------|---------------------|---------------------|---------------------|------|
| RmsNorm (input, 1 call) | 12.8 | 0.003 | 17.5 | input norm 在 expand 前 |
| O proj (24 calls) | 294.2 | 0.152 | 522.7 | compress 后, 唯一 tokens |
| InplaceAddRmsNorm (47 calls) | 411.1 | 0.374 | 972.1 | post-attn + post-FFN, 唯一 |
| Gate+Up (48 calls) | 374.1 | 1.496 | 2,618.1 | FFN, 唯一 |
| SiLU*gate (24 calls) | 271.9 | 0.294 | 712.9 | FFN, 唯一 |
| Down (24 calls) | 182.0 | 0.819 | 1,410.5 | FFN, 唯一 |
| Sub (1 call) | — | — | 3.6 | prefix 模式消除 |
| **合计** | **1,546.1** | **3.138** | **6,252.3** | |

### 2.3 非受益算子 (两种模式均处理全 batch tokens)

| 算子 | 固定开销 F (us/iter) | 可变开销 V (us/token) | 全batch时间 (1500tok) | 说明 |
|------|---------------------|---------------------|---------------------|------|
| Q proj (48 calls) | 458.2 | 0.067 | 558.7 | 全batch |
| K+V proj (24 calls) | 286.3 | 0.150 | 511.3 | 全batch |
| FIA (24 calls) | 2,527.9 | 0.131 | 2,724.9 | 全batch |
| ApplyRotary (24 calls) | 244.4 | 0.132 | 442.5 | 全batch |
| lm_head (1 call) | 8.4 | 0.000 | 8.5 | 最后token |
| RmsNorm (final, 1 call) | 12.8 | 0.003 | 17.3 | 最后token |
| GatherV2 (embedding, 2 calls) | 31.6 | 0.026 | 70.2 | launch主导 |
| Add (1 call) | 11.4 | ~0 | 9.5 | 最后token |
| **合计** | **3,581.0** | **0.509** | **4,342.9** | |

### 2.4 模型验证

```
总固定 = 1,546.1 + 3,581.0 = 5,127.1 us/iter
总可变 = 3.138 + 0.509 = 3.647 us/token

seq150 (1500 tok): 5,127.1 + 3.647 × 1500 = 10,598 ≈ 10,596 ✓
seq218 (2180 tok): 5,127.1 + 3.647 × 2180 = 13,078 ≈ 13,073 ✓
```

### 2.5 关键比例

| 指标 | seq150 | seq218 |
|------|--------|--------|
| 受益算子总时间 | 6,252 us (59.0%) | 7,441 us (56.9%) |
| 受益算子可变部分 | 4,707 us (44.4%) | 6,841 us (52.3%) |
| 受益算子固定部分 | 1,546 us (14.6%) | 1,546 us (11.8%) |
| 非受益算子总时间 | 4,343 us (41.0%) | 5,632 us (43.1%) |

> **受益算子可变部分** = V_benefit × Total_tokens = 3.138 × 1500 = 4,707 us
> 这是 prefix caching 理论上能节省的**最大上限** (100% 去重, 零开销)。

## 3. 理论最高收益计算

### 3.1 节省公式

```
Savings(r) = Total_tokens × r × V_benefit
           = Total_tokens × r × 3.138

Net(r) = Savings(r) - Overhead_GatherV2 - Overhead_AttentionDegradation
```

其中:
- `r` = 去重率 = prefix_len × (batch-1) / (seq_len × batch)
- `Overhead_GatherV2` ≈ 670~750 us/iter (50 次 × ~14 us, 与去重率无关)
- `Overhead_AttentionDegradation` ≈ 168~300 us/iter (GatherV2 内存竞争导致)

| 去重率 | seq150 节省 (us) | 占比 | seq218 节省 (us) | 占比 |
|--------|-----------------|------|-----------------|------|
| 50% | 2,714 | 25.6% | 3,943 | 30.2% |

## 4. Batch 规模扩展

### 4.1 更大 batch 的收益放大

增大 batch 时:
- 最大去重率 r_max = (B-1)/B → 趋近 100%
- 总 token 数 = seq_len × B → 线性增长
- 绝对节省 = seq_len × (B-1) × V_benefit → 线性增长
- GatherV2 开销 ≈ 恒定 (~670 us, 50 次/iter)
- 非受益算子也随 batch 增长 (处理全 batch)

**场景 B (理想 FFN 去重), seq=150, prefix=150 (全共享):**

| batch | 总tokens | 去重率 | 节省 (us) | 无prefix总时间 (us) | 收益率 | GatherV2占比 |
|-------|---------|--------|----------|-------------------|-------|------------|
| 10 | 1,500 | 90% | 4,236 | 10,596 | 40.0% | 6.3% |
| 20 | 3,000 | 95% | 8,943 | 16,068 | 55.7% | 4.2% |
| 50 | 7,500 | 98% | 23,064 | 32,480 | 71.0% | 2.1% |
| 100 | 15,000 | 99% | 46,599 | 59,832 | 77.9% | 1.1% |

> 无prefix总时间 = 5,127 + 3.647 × 总tokens (线性模型)
> 节省 = 总tokens × r × 3.138

> **注意**: 大 batch 下线性模型可能失效, 因为:
> 1. Attention 的 O(n²) 复杂度 (FlashAttention 缓解但未消除)
> 2. HBM 带宽瓶颈
> 3. Cube core 饱和后 MatMul 不再线性加速
>
> 以上数据仅适用于线性模型有效范围 (batch ≤ ~20, seq × batch ≤ ~5000)。

### 4.2 GatherV2 开销的占比衰减

| batch | GatherV2 开销 (us) | 总时间 (us) | GatherV2 占比 |
|-------|-------------------|------------|-------------|
| 10 | 670 | 10,596 | 6.3% |
| 20 | 670 | 16,068 | 4.2% |
| 50 | 670 | 32,480 | 2.1% |
| 100 | 670 | 59,832 | 1.1% |

> batch 越大, GatherV2 开销越可忽略, 当前实现的 break-even 点越低, prefix caching 越容易成正收益。

## 5. 不可压缩基线分析

### 5.1 哪些时间无法被 prefix caching 节省

| 类别 | seq150 (us) | 占比 | 说明 |
|------|------------|------|------|
| 非受益算子 (全batch) | 4,343 | 41.0% | Attention + Q/K/V/Rotary, 处理全batch |
| 受益算子固定开销 | 1,546 | 14.6% | kernel launch + tiling setup, 与token数无关 |
| 非受益算子固定开销 | 3,581 | 33.8% | (包含在上面 4,343 中) |
| **不可压缩基线** | **5,889** | **55.6%** | 非受益 + 受益固定 |
| **可压缩上限** | **4,707** | **44.4%** | 受益可变部分 |

### 5.2 不可压缩基线的构成

```
不可压缩 = 非受益算子 (4,343 us) + 受益算子固定开销 (1,546 us) = 5,889 us

非受益算子分解:
  FIA 固定:     2,528 us (43.0%) ← Attention 是最大不可压缩项
  Q proj 固定:    458 us (7.8%)
  ApplyRotary:    244 us (4.1%)
  K+V proj 固定:  286 us (4.9%)
  其他固定:       827 us (14.1%)

受益算子固定:
  InplaceAddRmsNorm: 411 us (7.0%)
  Gate+Up 固定:      374 us (6.4%)
  O proj 固定:       294 us (5.0%)
  SiLU*gate 固定:    272 us (4.6%)
  Down 固定:         182 us (3.1%)
  其他固定:           13 us (0.2%)
```

> **FIA 固定开销 (2,528 us) 是最大的不可压缩项**, 占不可压缩基线的 43%。
> 即使 100% 去重, attention 仍需 2,528 us (固定) + 0.131 × unique_tokens。
> 这也是场景 C (全链路去重) 能突破 44.4% 上限的原因——将 FIA 的可变部分也消除。

## 6. 实测验证

### 6.1 当前实测 (prefix=20, dedup=12%) vs 理论模型

| 指标 | 实测 (us/iter) | 理论模型 (us/iter) | 差异 | 说明 |
|------|---------------|-------------------|------|------|
| Gate+Up 节省 | 239 | 270 | -12% | 实测低于理论 (非线性/chip差异) |
| Down 节省 | 90 | 148 | -39% | 实测显著低于理论 |
| O proj 节省 | 14 | 28 | -50% | 实测低于理论 |
| AddRmsNorm 节省 | 12 | 67 | -82% | 实测远低于理论 |
| SiLU*gate 节省 | 67 | 53 | +26% | 实测高于理论 |
| **总节省** | **408** | **565** | **-28%** | 实测为理论的 72% |

> 实测总节省 (408 us) 为理论模型 (565 us) 的 72%, 差异来自:
> 1. **芯片差异**: 无prefix在device 8, 有prefix在device 4 (存在个体差异)
> 2. **非线性scaling**: 低token数时固定开销占比更高, 实际效率低于线性外推
> 3. **Attention退化**: +168 us (GatherV2 内存竞争)
> 4. **GatherV2开销**: +672 us (50次/iter)

### 6.2 修正后的保守估算

考虑到实测效率为理论的 72%, 修正后的 break-even 和最高收益:

| 场景 | seq150 break-even | seq150 max收益 (90%) | seq218 break-even | seq218 max收益 (90%) |
|------|-------------------|---------------------|-------------------|---------------------|
| 理论模型 | r=17.8%, P=30 | 32.1% | r=15.4%, P=37 | 39.1% |
| **修正 (×0.72)** | r=24.7%, P=41 | 24.5% | r=21.4%, P=52 | 29.5% |
| 实测break-even (文档) | P≈51 | — | P≈47 | — |

> 修正后的 break-even (P=41) 接近文档估算 (P≈47-51), 差异来自文档只计 FFN 节省。
> 修正系数 0.72 反映了: 线性模型高估 + chip差异 + attention退化。

```
prefix_len ≥ 0.15 × seq_len  (batch=50)
```

即 prefix 需占序列长度的 15-25% 以上才值得启用。

## 8. 收益上限的物理约束

### 8.1 为什么最高收益不能超过 ~50% (当前架构)

```
总时间 = 可压缩 (44.4%) + 不可压缩 (55.6%)

不可压缩构成:
  1. Attention 固定开销:  2,528 us (23.9%) ← 最大瓶颈
  2. Q/K/V/Rotary:         1,053 us (9.9%) ← 全batch, 不可去重
  3. 各算子固定开销:       1,989 us (18.8%) ← launch/tiling, 与token无关
  4. 其他:                  319 us (3.0%) ← lm_head/Add/GatherV2
```

### 8.2 突破上限的路径

| 优化路径 | 突破的上限 | 预期收益 | 难度 |
|---------|-----------|---------|------|
| GatherV2 融合 (场景B) | 消除 670 us 开销 | +6.3% → 40% | 中 (需算子融合) |
| Attention 也去重 (场景C) | 消除 FIA 可变 0.131 us/tok | +6.1% → 46% | 高 (需 KV cache 共享) |
| Q/K/V proj 去重 (场景C) | 消除 0.217 us/tok | +3.1% → 49% | 高 (需重构 attention) |
| 减少固定开销 | 减少 launch/tiling | 取决于优化 | 中 (需 kernel 优化) |
| 增大 batch | r→100%, 开销占比↓ | 55-78% (线性模型) | 低 (配置调整) |

### 8.3 增大 batch 是最简单的收益放大器

| batch | r_max | GatherV2占比 | 当前实现max收益 | 理想max收益 |
|-------|-------|------------|---------------|------------|
| 10 | 90% | 6.3% | 32% | 40% |
| 20 | 95% | 4.2% | 47% | 53% |
| 50 | 98% | 2.1% | 64% | 68% |
| 100 | 99% | 1.1% | 72% | 75% |

> batch=50 时, 即使当前实现 (含 GatherV2 开销), 理论收益也可达 64%。
> 前提: 线性模型有效 (实际受 HBM 带宽和 attention O(n²) 约束)。

## 9. 结论

### 9.1 理论最高收益

| 维度 | seq150 (batch=10) | seq218 (batch=10) |
|------|-------------------|-------------------|
| **当前实现最高收益** (90%去重, 含GatherV2开销) | **32.1%** (3,398 us) | **39.1%** (5,106 us) |
| **理想FFN去重最高收益** (90%去重, 零开销) | **40.0%** (4,236 us) | **47.1%** (6,156 us) |
| **全链路去重最高收益** (90%去重, 含Attention) | **46.1%** (4,884 us) | **54.3%** (7,103 us) |
| **绝对理论极限** (100%去重, 全链路, 零开销) | **51.6%** (5,470 us) | **60.8%** (7,950 us) |

### 9.2 关键发现

1. **当前实现的理论上限为 32-39%** (batch=10, 90%去重), 但需 prefix_len ≥ seq_len, 实际场景中难以完全达到
2. **可压缩部分占 44%** (受益算子可变开销), 不可压缩部分占 56% (非受益算子 + 固定开销)
3. **Attention 是最大不可压缩项** (2,528 us 固定 + 0.131 us/tok 可变), 占不可压缩基线的 43%
4. **GatherV2 开销是当前瓶颈** (+838 us), 但随 batch 增大占比衰减, batch=50 时仅占 2%
5. **增大 batch 是最简单的收益放大器**: batch=50 时当前实现可达 64% 收益
6. **全链路去重 (Attention+KV cache 共享) 可突破 44% 上限**, 达 46-54%
7. **实测效率为理论模型的 72%**, 主要因芯片差异和非线性 scaling

### 9.3 Break-even 条件

| 实现 | break-even 去重率 | break-even prefix_len (seq150) | 说明 |
|------|------------------|-------------------------------|------|
| 当前实现 (理论模型) | 17.8% | 30 | 含 GatherV2 + attention退化 |
| 当前实现 (修正×0.72) | 24.7% | 41 | 考虑实测非线性 |
| 当前实现 (实测, 文档) | ~30% | 51 | 最保守估计 |
| 理想实现 (零开销) | 0% | 0 | 任何 prefix 都有正收益 |

### 9.4 优化建议优先级

| 优先级 | 优化方向 | 预期收益提升 | 难度 |
|--------|---------|------------|------|
| P0 | 增大 batch (配置调整) | +15-40% | 低 |
| P1 | GatherV2 融合到相邻算子 | +6-8% | 中 |
| P2 | 增大 prefix_len (业务侧) | 线性增长 | 低 |
| P3 | Attention KV cache 共享 | +6-8% | 高 |
| P4 | 减少固定开销 (kernel优化) | +3-5% | 中 |

## 11. 附录 B: 公式汇总

```
去重率:           r = prefix_len × (batch - 1) / (seq_len × batch)
最大去重率:       r_max = (batch - 1) / batch

FFN侧节省:        S_ffn(r) = seq_len × batch × r × V_benefit
                  V_benefit = 3.138 us/token (当前架构)
                  V_full = 3.618 us/token (全链路)

净收益(当前):     Net(r) = S_ffn(r) - Overhead_gather - Overhead_attn
                  Overhead_gather ≈ 670 us (batch=10)
                  Overhead_attn ≈ 168 us (seq150) / 300 us (seq218)

Break-even:       r = (Overhead_gather + Overhead_attn) / (Total_tokens × V_benefit)

理论极限:         Limit = Total_variable / Total_time
                  FFN侧: V_benefit × Total_tokens / Total_time
                  全链路: V_full × Total_tokens / Total_time
```
